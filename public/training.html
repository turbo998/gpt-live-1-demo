MODULE 01 · EXECUTIVE SUMMARY & PARADIGM SHIFT

从“串行语音机器人”到“全双工自然交谈 + 旁路受控执行”

为什么传统级联语音机器人在真实门店、座舱和客服热线中屡屡受挫？本节帮助合作伙伴工程师用三句话建立对 Azure Voice Live API 与 GPT-Live-1 的准确架构认知。

全双工边说边听 137 Locales · 30+ Regions (含中国区) 快慢双脑解耦

1. 传统语音机器人的三大工程顽疾Legacy Pain

  • 机械抢话与误打断：传统能量阈值 VAD 把用户的自然附和（“嗯哼、对”）、思考停顿、咳嗽或旁人说话全部当作打断指令，导致对话支离破碎。
  • 级联交接损耗与副语言丢失：`STT ➔ LLM ➔ TTS` 三段串行不仅累加延迟，还在转文字瞬间丢失了用户的情绪、迟疑与语调重音。
  • 模型幻觉与业务失控：若让端到端语音大模型直接口头承诺库存、算账或改单，极易出现算错价格或口头“假取消”。

2. Azure Voice Live API 的核心定义Realtime Interface

  • 它是什么：一个高性能、生产级的 Realtime LLM 接口层，让云上任意大模型（Foundry 1000+ 模型与自建 BYOM）即插即用获得“能听会说”的实时语音交互与 Agent 编排能力。
  • 它不是什么：它不是单一 LLM、不是封闭的成品对话机器人、不是呼叫中心（CCaaS）系统，不会与合作伙伴的行业应用争抢业务层。
  • 四档可演进管线：在同一套 API 契约下支持 全双工 (`GPT-Live-1`)、语音到语音 (`GPT Realtime`)、混合式 (`Hybrid`)、级联式 (`Cascaded`) 灵活选型。

3. GPT-Live 参考架构的“快慢双脑”哲学Reference Pattern

  • 快脑（WebRTC 媒体直连 `gpt-live-1`）：负责毫秒级全双工倾听、自然口语应答、附和承接与中途打断刹停。
  • 慢脑（旁路 WSS + `gpt-4.1-mini` Responses）：负责确定性时间短路、安全算式、Open-Meteo 天气消歧、饮品菜单同音词检索与 Bing 联网溯源。
  • 受控交接（`SpeechDelivery` 状态机）：后台结果按 220 字分片注入 `commentary`，待用户安静后触发 `instructions` 口播，超时自动降级文字重播。

① 解决什么合作伙伴工程痛点？

企业客户往往同时拥有网页、App、SIP 呼叫中心（Genesys/Twilio/ACS）与车载/IoT 硬件。过去每增加一种终端或更换底层大模型，合作伙伴都要重写一套音频流编解码、回声消除、断句 VAD 和工具调用胶水代码。

② 架构图核心机制拆解（自左向右）

  • 全渠道与三协议（`WebSocket / WebRTC / SIP` + 4 语言 SDK）：浏览器/App 走 WebRTC 享低延迟与端侧 AEC；服务端走 WebSocket；传统电话网通过与 M365 同源的 IC3 Media Gateway 原生对接 SIP/RTP。
  • 实时音频 DSP 层：云端内置全双工语义轮次检测（Semantic VAD / EoU）、播放参考回声消除与环境降噪。
  • `VOICE LIVE AGENT` 运行时 Harness：原生提供 `Sub-agent`、`Function Calling`、`MCP 工具`、`Foundry Agent`、`主动消息` 与 `上下文静默管理`。
  • 两条模型路径：既可直连 Foundry 模型目录（1000+ 开源与商业模型），也可通过 BYOM 接入客户自建/微调模型。

③ 面向客户的商业与交付价值

一次集成，全球复用：覆盖 137 种地区语言与全球 30+ 区域（含中国大陆世纪互联 China East 2 / North 2 / North 3），提供照片级/视频级 Avatar 数字人同步驱动，将多渠道语音 Agent 交付周期从数月缩短至数周。

④ 售前与架构师必讲定位边界

向客户强调：Voice Live API 不是单一 LLM，也不是用来替代客户现有 CRM/呼叫中心平台的封闭黑盒，而是赋能任意业务系统“听得懂、说得自然、调得动工具”的标准实时语音底座。

① 解决什么架构选型痛点？

不同业务对“拟人交互度、品牌专属音色、垂直领域生僻词准确率、单分钟成本”的权重截然不同。单一端到端模型无法同时满足“0.1美元/小时超低成本”和“企业定制品牌音色”，单一级联架构又无法实现“边说边听自然附和”。

② 左侧四层语音管线（Four-Tier Pipeline）如何选型？

  • ① 全双工 (`GPT-Live-1`)：单模型同时对输入与输出音频联合推理（边说边听），抗干扰探针通过率 95% (20/21)，适合旗舰导购、座舱免唤醒与高拟人陪练。
  • ② 语音到语音 (`GPT Realtime · Azure Realtime`)：原生多模态端到端语音交互。
  • ③ 混合式 (`Semantic VAD·EoU + GPT Realtime 2.1/1.5 + Azure Speech TTS`)：用多模态模型直接听懂语音，用 DragonHDFlash / Custom Voice 发出品牌定制声音（印度 Paytm 20万通/天生产验证，P50 590ms）。
  • ④ 级联式 (`Semantic VAD·EoU + Azure STT + Foundry/BYO LLM + Azure TTS`)：最高术语可控性（Custom Speech 饮品同音词 12/12 修正）+ 最低 STT 成本（`MAI-Transcribe-2` $0.10/h）+ 任意大模型（GPT/Claude/Gemini/OSS）。

③ 右侧「统一任务委派（Task Delegation）」的核心架构价值

无论左侧采用哪一档语音管线，右侧均通过统一的 Task Delegation 将深度推理、RAG、搜索与工具调用委派给 Foundry 智能体、GPT/Claude/Gemini、OSS 或客户自有后端——真正实现“快脑管实时语音交互，慢脑管严谨业务逻辑”。

④ 合作伙伴架构设计黄金法则

不要在客户立项第一天争论“端到端还是级联”：基于 Voice Live API 统一契约，高端顾问场景用 Tier ① 全双工，高并发客服热线用 Tier ③ 混合式，强专有名词/成本敏感场景用 Tier ④ 级联式，后台工具层代码 100% 复用。

① 为什么初版 Demo 要这样设计？（解决三大落地难题）

1) `gpt-live-1` 不签发浏览器临时客户端密钥，如何保证前端零密钥泄露？
2) 如果音频流经过应用服务器转发，Node.js 带宽与抖动如何承受？
3) 后台工具查出长答案后，如何安全交还给正在说话或倾听的语音模型？

② 三平面职责分离机制（Three-Plane Separation）

  • 平面 1 · 会话握手与托管身份面（HTTPS + SDP）：浏览器向受保护的 Linux App Service B1 (`West US 2`) 提交 SDP；后端通过 Azure Managed Identity (`Cognitive Services OpenAI User`) 动态获取 Entra 令牌创建会话，云端不存模型 API Key，浏览器端零凭据暴露。
  • 平面 2 · 实时媒体直连面（Browser ⇄ WebRTC ⇄ `gpt-live-1`）：SDP 建连后，浏览器麦克风/扬声器与 `East US 2` 的 `gpt-live-1` 建立点对点 WebRTC 音频与 `oai-events` 数据通道，音频流不绕行应用服务器。
  • 平面 3 · 旁路控制与受控委派面（WSS `/live/sessions/{id}/attach`）：Node.js 挂载旁路 WebSocket，监听 `session.delegation.created`；独立时钟走 `fastTimeAnswer`（0 Token），天气/算式/菜单/Bing 联网走 `gpt-4.1-mini` (`/responses`, `store:false`)，再由 `SpeechDelivery` 分片注入并择机 Nudge 口播。

③ 跨区域拓扑说明（West US 2 应用 + East US 2 模型）

由于音频流在浏览器与 `East US 2` 模型间直连，App Service 仅在建连与旁路工具触发时参与；因此缩短 Web 应用与用户的距离只加速页面加载与握手，不改变浏览器到语音模型区域的物理网络延迟。

④ 必须向伙伴工程师讲透的四大工程红线

  • 语音打断 ≠ 业务事务回滚：Barge-in 仅停止语音播放，不会撤销已发往后端的请求。
  • 口头回答 ≠ 权威业务状态：必须以“查询来源与工具记录”面板中的结构化结果为准。
  • GlobalStandard ≠ 区域数据驻留承诺：有严格驻留要求需评估区域级或合规部署。
  • 停止 Web App ≠ 停止 App Service Plan 计费：B1 Plan ($0.017/h) 需缩容或清理才停计费。

① 解決什麼合作夥伴工程痛點？

企業客戶往往同時擁有網頁、App、SIP 聯絡中心（Genesys/Twilio/ACS）與車載/IoT 硬體。過去每增加一種終端或更換底層大模型，合作夥伴都要重寫一套音訊流編解碼、回聲消除、斷句 VAD 和工具調用膠水程式碼。

② 架構圖核心機製拆解（自左向右）

  • 全通路與三協議（`WebSocket / WebRTC / SIP` + 4 語言 SDK）：瀏覽器/App 走 WebRTC 享低延遲與端側 AEC；伺服端走 WebSocket；傳統電話網通過與 M365 同源的 IC3 Media Gateway 原生對接 SIP/RTP。
  • 即時音訊 DSP 層：雲端內建全雙工語義輪次檢測（Semantic VAD / EoU）、播放參考回聲消除與環境降噪。
  • `VOICE LIVE AGENT` 運行時 Harness：原生提供 `Sub-agent`、`Function Calling`、`MCP 工具`、`Foundry Agent`、`主動訊息` 與 `上下文靜默管理`。
  • 兩條模型路徑：既可直連 Foundry 模型目錄（1000+ 開源與商業模型），也可通過 BYOM 接入客戶自建/微調模型。

③ 面向客戶的商業與交付價值

一次集成，全球複用：覆蓋 137 種地區語言與全球 30+ 區域（含中國大陸世紀互聯 China East 2 / North 2 / North 3），提供照片級/視訊級 Avatar 數位人同步驅動，將多渠道語音 Agent 交付週期從數月縮短至數週。

④ 售前與架構師必講定位邊界

向客戶強調：Voice Live API 不是單一 LLM，也不是用來替代客戶現有 CRM/聯絡中心平臺的封閉黑盒，而是賦能任意業務系統“聽得懂、說得自然、調得動工具”的標準即時語音底座。

① 解決什麼架構選型痛點？

不同業務對“擬人互動度、品牌專屬音色、垂直領域生僻詞準確率、單分鐘成本”的權重截然不同。單一端到端模型無法同時滿足“0.1美元/小時超低成本”和“企業定製品牌音色”，單一串接級聯架構又無法實現“邊說邊聽自然附和”。

② 左側四層語音管線（Four-Tier Pipeline）如何選型？

  • ① 全雙工 (`GPT-Live-1`)：單模型同時對輸入與輸出音訊聯合推理（邊說邊聽），抗干擾探針通過率 95% (20/21)，適合旗艦導購、座艙免喚醒與高擬人陪練。
  • ② 語音到語音 (`GPT Realtime · Azure Realtime`)：原生多模態端到端語音交互。
  • ③ 混合式 (`Semantic VAD·EoU + GPT Realtime 2.1/1.5 + Azure Speech TTS`)：用多模態模型直接聽懂語音，用 DragonHDFlash / Custom Voice 發出品牌定製聲音（印度 Paytm 20萬通/天生產驗證，P50 590ms）。
  • ④ 串接級聯式 (`Semantic VAD·EoU + Azure STT + Foundry/BYO LLM + Azure TTS`)：最高術語可控性（Custom Speech 飲品同音詞 12/12 修正）+ 最低 STT 成本（`MAI-Transcribe-2` $0.10/h）+ 任意大模型（GPT/Claude/Gemini/OSS）。

③ 右側「統一任務委派（Task Delegation）」的核心架構價值

無論左側採用哪一檔語音管線，右側均通過統一的 Task Delegation 將深度推理、RAG、搜尋與工具調用委派給 Foundry 智能體、GPT/Claude/Gemini、OSS 或客戶自有後端——真正實現“快腦管即時語音互動，慢腦管嚴謹業務邏輯”。

④ 合作夥伴架構設計黃金法則

② 三平面職責分離機製（Three-Plane Separation）

  • 平面 1 · 工作階段握手與受控識別 (Managed Identity)面（HTTPS + SDP）：瀏覽器向受保護的 Linux App Service B1 (`West US 2`) 提交 SDP；後端通過 Azure Managed Identity (`Cognitive Services OpenAI User`) 動態獲取 Entra 令牌建立會話，雲端不存模型 API Key，瀏覽器端零憑據暴露。
  • 平面 2 · 即時媒體直連面（Browser ⇄ WebRTC ⇄ `gpt-live-1`）：SDP 建連後，瀏覽器麥克風/揚聲器與 `East US 2` 的 `gpt-live-1` 建立點對點 WebRTC 音訊與 `oai-events` 資料通道，音訊流不繞行應用伺服器。
  • 平面 3 · 旁路控製與受控委派面（WSS `/live/sessions/{id}/attach`）：Node.js 掛載旁路 WebSocket，監聽 `session.delegation.created`；獨立時鐘走 `fastTimeAnswer`（0 Token），天氣/算式/菜單/Bing 聯網走 `gpt-4.1-mini` (`/responses`, `store:false`)，再由 `SpeechDelivery` 分片注入并擇機 Nudge 口播。

③ 跨區域拓撲說明（West US 2 應用 + East US 2 模型）

由於音訊流在瀏覽器與 `East US 2` 模型間直連，App Service 僅在建連與旁路工具觸發時參與；因此縮短 Web 應用與用戶的距離隻加速頁面載入與握手，不改變瀏覽器到語音模型區域的物理網路延遲。

2. Core Definition of Azure Voice Live APIRealtime Interface

④ Positioning Boundary for Solution Architects

Emphasize to customers: Voice Live API is not a single LLM and not a black-box replacement for existing CRM/CCaaS platforms; it is the standardized real-time voice runtime that enables any business application to listen, speak naturally, and invoke tools safely.

① What Architecture Trade-Off Does It Solve?

Different workloads weight conversational naturalness, custom brand voice, domain-specific vocabulary accuracy, and per-minute cost very differently. No single end-to-end model can simultaneously deliver $0.10/hr ultra-low STT cost and custom brand TTS, while pure cascaded pipelines cannot listen while speaking.

② How to Select Among the Four Voice Pipeline Tiers (Left Plane)

  • ① Full-Duplex (GPT-Live-1): Single model jointly reasons over simultaneous input and output audio streams, achieving a 95% (20/21) noise/turn-taking pass rate—ideal for flagship retail advisors, hands-free smart cockpits, and coaching.
  • ② Speech-to-Speech (GPT Realtime · Azure Realtime): Native multimodal end-to-end speech interaction.
  • ③ Hybrid (Semantic VAD·EoU + GPT Realtime 2.1/1.5 + Azure Speech TTS): Understands audio natively via multimodal LLM while speaking with DragonHDFlash / Custom Voice (proven in Paytm production at 200K+ calls/day, P50 590ms).
  • ④ Cascaded (Semantic VAD·EoU + Azure STT + Foundry/BYO LLM + Azure TTS): Maximum terminology control (Custom Speech 12/12 beverage homophone fix) + lowest STT cost (MAI-Transcribe-2 at $0.10/hr) + any text LLM (GPT/Claude/Gemini/OSS).

③ Architectural Value of Unified Task Delegation (Right Plane)

Regardless of which voice pipeline tier runs on the left, the right plane uses unified Task Delegation to route deep reasoning, RAG, web search, and transactional tools to Foundry Agents, GPT/Claude/Gemini, OSS, or customer backends—cleanly decoupling the Fast Voice Brain from the Slow Business Brain.

④ Partner Architecture Golden Rule

Never get stuck debating "end-to-end vs. cascaded" on Day 1: under the unified Voice Live API contract, use Tier ① Full-Duplex for premium concierge, Tier ③ Hybrid for high-concurrency brand hotlines, and Tier ④ Cascaded for heavy domain jargon or cost-sensitive scale—while reusing 100% of backend tool code.

① Why Is the Reference Demo Designed This Way? (3 Production Challenges)

1) Since gpt-live-1 does not issue ephemeral browser client keys, how do we guarantee zero credential leakage in the frontend?
2) If raw audio were proxied through Node.js, how would we avoid server bandwidth bottlenecks and jitter?
3) When a backend tool returns a multi-paragraph answer, how is it safely handed back to an active voice model?

② Three-Plane Separation of Concerns

  • Plane 1 · Session Handshake & Managed Identity (HTTPS + SDP): Browser posts its SDP offer to protected Linux App Service B1 (West US 2); backend uses Azure Managed Identity (Cognitive Services OpenAI User) to create the East US 2 /live/sessions session and complete WebRTC SDP exchange—zero keys in browser.
  • Plane 2 · Direct Real-Time Media Plane (Browser ⇄ WebRTC ⇄ gpt-live-1): Once SDP completes, browser mic/speaker connects peer-to-peer with gpt-live-1 in East US 2 over WebRTC audio + oai-events data channel—audio never hairpins through App Service.
  • Plane 3 · Sideband Control & Controlled Delegation (WSS /live/sessions/{id}/attach): Node.js attaches a sideband WebSocket listening for session.delegation.created; standalone clock queries short-circuit via fastTimeAnswer (0 LLM tokens), while weather/math/menu/Bing search route to gpt-4.1-mini (/responses, store:false) and return via SpeechDelivery.

③ Cross-Region Topology Note (West US 2 App + East US 2 Models)

Because WebRTC audio flows directly between the user's browser and East US 2 models, App Service participates only during session setup and sideband tool triggers. Moving the web app closer to users speeds up page load and SDP setup, but voice latency is governed by physical network distance to the model region.

④ Four Engineering Red Lines Every Partner Engineer Must Know

  • Voice Barge-In ≠ Transaction Rollback: Interrupting speech stops playback on the client; it does not roll back in-flight backend requests.
  • Spoken Reply ≠ Authoritative Business State: Always treat structured records in the "Sources & Tool Audit" panel as the source of truth.
  • GlobalStandard ≠ Regional Data Residency Guarantee: Workloads with strict residency mandates require regional or sovereign deployments.
  • Stopping the Web App ≠ Stopping App Service Plan Billing: Linux B1 Plan ($0.017/hr) continues billing until scaled down or deleted.
